The metR HTML to DITA converter does not rely on visual formatting alone. It reads structural information from HTML elements and semantic markup. When those elements are applied correctly, the converter and AI Agent can:

  • Generate a root Ditamap and child Ditamaps from the index file, ZIP folder name, or document title.
  • Detect topic boundaries from heading levels and establish the Ditamap hierarchy.
  • Classify topic types: concept (descriptive), task (procedural), reference (tabular or lookup), or troubleshooting.
  • Convert paragraphs, lists, tables, images, links, inline formatting, and code blocks to valid DITA elements.
  • Infer metadata — short descriptions, keywords, index terms, author, and revision history — from <head> meta tags and structured body elements.
  • Flag issues such as missing short descriptions, invalid links, duplicate IDs, orphan topics, and improper nesting for human review.

This section covers the Table of Contents and Root Index — the navigation structure that maps the publication hierarchy and serves as the converter's primary entry point for building the root DITA map — and two scenarios: a root index file present in the package, and a missing root index file. The converter reads the root index to construct the DITA map hierarchy and topic references; when no root index is present, it falls back to the package folder name or filename as the root map title.

A table of contents or root index is the navigation structure of a publication. It declares the document's complete hierarchy in one place — the titles, sequence, and parent-child relationships of all sections, chapters, and topics — and provides the entry point from which readers and systems navigate the entire deliverable.

For the publishing system, the table of contents or root index is the structural anchor of the entire output — every generated navigation artifact, including the PDF bookmark panel, the HTML5 navigation tree, the WebHelp TOC panel, and the DITA map hierarchy, derives from this structure.

Note: The converter reads it to build the DITA map hierarchy and then discards it — the publishing transform regenerates the navigation structure at build time from the assembled DITA map, ensuring it always reflects the actual content rather than a manually maintained list that can fall out of sync.

In a well-structured HTML package, the table of contents is provided by the navigation structure in the index.html or index.htm file. Each navigation link references an HTML document within the publication, and the order and nesting of these links establish the hierarchy of the generated documentation.

The converter reads the navigation structure in the index file to generate the root Ditamap hierarchy. The table of contents itself is not converted into a standalone DITA topic. Instead, each navigation link becomes a corresponding <mapref> or <topicref> in the generated root Ditamap, preserving the organization of the original HTML publication.

Important: Ensure that the table of contents accurately reflects the intended publication hierarchy and that every navigation link references a valid HTML file. Missing, incorrect, or incomplete navigation links result in an incomplete Ditamap hierarchy and may exclude topics from the generated publication.

Metadata is structured information about a document, separate from its body content. It records attributes such as authorship, creation and revision dates, and classification tags. Both carry the same categories of information but in different forms that the converter must recognize and extract from each location.

The converter and AI Agent map this metadata to the DITA <prolog> element in the generated topic, making it available to downstream publishing tools, content management systems, and search indexes.

This section covers the Heading style in HTML — its role as the primary structural mechanism that organizes a document's content into a named, hierarchical sequence of sections — and four scenarios: headings applied in correct sequential order, a heading level skipped in the hierarchy, a top-level heading absent from the document, and consecutive headings with no body content between them. The converter reads each heading level to construct the DITA map hierarchy, generating sub-maps, topic files, and topic type classifications from the heading sequence and the content that follows each heading.

A Headingstyle marks the beginning of a named section of content and assigns it a rank in the document hierarchy. It is the primary structural mechanism of any technical document — headings divide continuous content into discrete, named units, establish the parent-child relationships between those units, and create the navigational backbone that readers and publishing systems depend on.

The heading hierarchy is expressed through levels: a top-level heading (Heading 1) names a major section; each lower-level heading (Heading 2 through Heading N) names a subsection within its parent. This ranked sequence carries the same structural meaning regardless of the format it is expressed. The level communicates the section's position in the hierarchy; the text communicates its subject.

Note: Only a semantically marked heading — applied through the document's native heading mechanism — creates a genuine section boundary that a converter, search engine, or publishing system can detect and act on.

In well-formed HTML, headings are applied sequentially without skipping levels. An <h1> is followed by one or more <h2> elements, each <h2> may contain one or more <h3> elements, and so on.

The converter reads the heading elements within the <body> of each HTML file to determine how many DITA topic files to generate, how to title and nest them in the Ditamap, and what topic type each one receives. It then analyzes the content that follows each heading, such as paragraphs, lists, and tables, to classify the resulting topic as Concept, Task, Reference, Troubleshooting, or Generic.

Abstract: This section covers the Paragraph style in HTML — its role as the primary carrier of explanatory, introductory, and transitional prose in any technical document — and four scenarios: a paragraph in a concept topic, a paragraph containing mixed inline character styles, a paragraph placed before the first heading, and a code paragraph. Paragraphsare the fundamental unit of prose communication in any technical publication. They carry three types of content as described below:

  • Explanatory content that defines concepts and terms.
  • Introductory content that sets the context for the structured elements that follow such as list, workflows, tables, procedures, and images.
  • Transitional content that connects sections and chapters through the document's logic.

This prose content is essential not only for readability but for building complete technical context, search discoverability and structural completeness.

Tip: A topic consisting only of a list or a table, with no surrounding prose, is a valid but an incomplete piece of technical communication. It is recommended to add the context to such structured elements.

In well-structured HTML, introductory paragraphs establish the context for a topic before lists, tables, or images present supporting information. Inline elements such as <strong>, <em>, <code>, and other recognized HTML tags provide semantic emphasis within the surrounding paragraph without changing its structural role.

The first introductory paragraph beneath a heading is also used to populate the generated <shortdesc&gt; element where applicable. Recognized inline HTML elements are converted to their equivalent DITA inline elements while preserving their semantic meaning. Empty paragraphs used only for visual spacing are ignored during conversion.

Important: Paragraphs should always appear within a heading-delimited section. A <p> element placed before the first heading is treated as pre-heading content and is processed according to a separate conversion rule. Use paragraphs to present meaningful content rather than visual spacing, and rely on recognized inline markup instead of manual formatting to convey emphasis.

An ordered list presents items in a defined sequence where the position of each item is significant. The ordered lists are universally used for step-by-step procedures, installation instructions, and ranked items.

For the reader, a numbered list communicates that sequence is contractual — item 2 depends on item 1 being completed, and performing the items out of order produces an incorrect or unsafe result. The list level is controlled by the Increase and Decrease Indent buttons, determines nesting depth: level 1 is the top level, level 2 is the first nested level, level 3 is the second, and so on. In well-structured HTML, ordered lists are created using native <ol> and <li> elements. Nested ordered lists represent subordinate sequences, while introductory paragraphs, images, tables, and notes provide supporting information without changing the sequential relationship between list items. A new <ol> element beginning after an existing list — rather than continuing it — signals a restarted or independent sequence rather than a continuation of the prior list.

The converter evaluates both the HTML list structure and the classified DITA topic type when processing an ordered list. Within Concept, Reference, and Generic topics, an HTML <ol> is converted to a DITA <ol>. Within a Task topic, the same <ol> is converted into <steps>, with each <li> mapped to a <step> containing a <cmd>. This section covers Unordered Lists — items presented as a co-equal collection where position does not affect meaning — and seven scenarios: consecutive bullet items, two-level nested bullet lists, three-level nested bullet lists, a block image between bullet items, a paragraph between bullet items, a table inside a list item, and an admonition between bullet items. The converter maps each unordered list to <ul><li> in concept and reference topics, or <choices> in task topics, based on the heading classification and content context.

An unordered list presents a collection of co-equal items where position does not affect meaning. The unordered list is typically used for prerequisites, supported platforms, product features, available options, feature list, and even terms and definition.

For the reader, a bulleted list communicates that the items are parallel and independent — none depends on another, and the set is complete as presented. The reader does not need to track position or sequence, only membership in the set.

The list level is controlled by the Increase and Decrease Indent buttons, determines nesting depth: level 1 is the top level, level 2 is the first nested level, level 3 is the second, and so on. Sometimes they are also defined by the tab alignment.

Note: The list level assigned by list controls is what drives the nesting structure in the DITA output.

In well-structured HTML, unordered lists are created using native <ul> and <li> elements. Nested unordered lists represent sub-groupings within a parent item, while introductory paragraphs, images, tables, and notes provide supporting information without altering the non-sequential relationship between items.

The converter evaluates both the HTML list structure and the classified DITA topic type when processing an unordered list. A <ul> immediately preceding an <ol> within the same topic typically signals prerequisite or conditional information rather than an independent list. Within Concept, Reference, and Generic topics, an HTML <ul> is converted to a DITA <ul>. Within a Task topic, a <ul> positioned immediately before the procedural <ol> is converted into <prereq>, with each <li> mapped to a <p> or <li> inside that section. The surrounding topic context determines whether the list remains a DITA <ul> or is transformed into another DITA structure, such as <prereq>.

This section covers Term Lists (Definition Lists) in HTML — structures that associate a term with its corresponding definition or description, emphasizing term-description relationships rather than value comparison across columns — and two scenarios: a native HTML <dl> element with <dt> and <dd> pairs, and a <ul> list following the bold-label pattern where each <li> begins with a <strong> term followed by a separator and definition text. A term list, also known as a definition list, is an HTML structure used to associate terms with their corresponding definitions or descriptions. It is commonly used to present technical terminology, configuration options, error codes, connection modes, and other reference information, with each term followed by one or more explanatory statements. Unlike a table, a definition list emphasizes the relationship between a term and its description rather than comparing values across multiple columns.

Term lists improve readability by allowing related definitions to be scanned without interrupting the flow of the surrounding content. Publishing systems, accessibility technologies, and content management systems rely on correctly structured definition lists to preserve the relationship between each term and its description across different output formats.

In well-structured HTML, term lists are authored either as native <dl> elements containing <dt> and <dd> pairs or as unordered lists where each <li> begins with a <strong> term followed by a separator and its corresponding definition. The native <dl> structure provides the clearest semantic representation, while the bold-label pattern offers an alternative that the converter can also recognize.

The converter detects both supported HTML patterns when generating DITA output. Native <dl> elements map directly to DITA <dl>, while recognized <ul> lists that follow the bold-label pattern are converted to the same DITA definition list structure. Each term becomes a DITA <dt>, each definition becomes a <dd>, and related pairs are grouped within a <dlentry>.

Important: Use native HTML <dl>, <dt>, and <dd> elements wherever possible to represent term-definition relationships. Although the converter recognizes supported <ul> patterns, native definition lists provide the clearest semantic structure and produce the most reliable conversion results.

Images and graphics are the primary means of communicating spatial relationships, component locations, interface states, system architectures, and process flows that text alone cannot convey efficiently. In technical publications, the image or graphic and its surrounding context carry equal structural weight.

The key differences between images and graphics are outlined below:

  • An image is a raster file — a grid of pixels captured or rendered at a fixed resolution. Images are resolution dependent, when scaled up beyond their original size, they lose sharpness. For example, screenshots, photographs, and scanned content (PNG, JPEG, BMP).
  • A graphic is a vector-based or constructed visual — built from mathematical shapes, lines, curves, and text rather than pixels. Graphics are resolution independent, when scaled up beyond their size does not lose its quality. For example, diagrams, flowcharts, and schematic illustrations (SVG, EMF, Visio, PDF).
Tip: Embed every image directly in the document body, apply meaningful alt text for accessibility, and add a caption to every figure that requires a title in the published output.

In well-structured HTML, images are referenced through valid src paths and positioned according to their intended role within the document. Images placed between block-level elements typically represent standalone figures, while images embedded within a paragraph support the surrounding text. When a <figure> element includes a <figcaption>, the caption provides a descriptive title for the generated figure.

The converter evaluates each <img> element together with its surrounding HTML context to determine the appropriate DITA structure. Standalone images are converted to <fig> elements containing <image>, inline images remain inline within the surrounding paragraph, and <figure> elements with <figcaption> generate titled DITA <fig> elements. During conversion, image files are extracted, converted to PNG format, stored in the media/ subfolder of the output directory, and referenced from the generated DITA topics using relative paths.

ATable is the primary structure for reference and lookup content. It is a structural mechanism to present information that has inherent row-and-column relationships — parameter names and their values, feature names and their states, error codes and their meanings, API fields and their data types.

A table reduces a lookup task from reading a paragraph to scanning a row and column. In DITA-XML, a table is structured data — each cell is a discrete, addressable unit that a transform can reformat for PDF, or online help output, filter by column for conditional publishing, and extract independently for reuse in other deliverables.

A table is an HTML structure used to organize related information into rows and columns. Represented by the native <table> element together with <tr>, <th>, and <td>, it presents information that is easier to compare, scan, or reference than the same information written as continuous text. Tables commonly represent configuration parameters, feature comparisons, error codes, API fields, and other structured lookup information.

The converter evaluates each table's structure — merged cells, the presence of a <caption>, column count, and the topic type it appears in — to determine the correct DITA output. A simple table maps to <simpletable>. A table with merged cells or a <caption> maps to a CALS <table> with <tgroup>. A two-column parameter table inside a Reference topic maps to <properties>. The converter relies entirely on the HTML table model, never on visual appearance.

Admonitions are paragraph-level notices that separate advisory, safety-related, or supplementary information from the surrounding body content. Admonitions identify information that requires immediate reader attention — safety warnings, usage restrictions, helpful tips, important prerequisites, and cautionary notices — and give it structural separation from the prose that surrounds it.

For readers and publishing systems, admonition apply stronger visual treatment or weight from tip through note through caution through warning through danger. Each one of them are distinct in admonition icons, background color, or text color.

In well-structured HTML, admonitions are commonly authored using <div>, <aside>, or <p> elements with recognizable class names or labels that indicate the type of advisory information.

The converter maps a paragraph with a recognized admonition style directly to <note type="[type]">. For a bold inline label, it applies content pattern recognition: it reads the opening text, removes the label, and maps the remaining text to the matching note type.

Mathematical equations communicate quantitative relationships that cannot be expressed accurately through prose alone. They are commonly used in engineering, scientific, financial, and technical documentation to represent formulas, calculations, algorithms, and symbolic expressions.

The mathematical equation can be inserted as:

Topic type classification is the process of assigning a heading-delimited section of HTML content to a specific DITA topic type. Unlike DITA, HTML does not explicitly identify a section as conceptual, procedural, reference, or troubleshooting content. Instead, the structure and purpose of a section are inferred from the heading and the HTML elements that follow it until the next heading of the same or higher level.

Accurate classification matters because every DITA topic type generates a distinct body element — <conbody>, <taskbody>, <refbody>, <troublebody>, or <body> — and each body element supports a specific content structure required for that topic type. A help system that filters search results by topic type, a content management system that applies different review workflows to tasks versus references, or a PDF generator that styles procedures with numbered callouts, all depend on the topic type being assigned correctly at conversion time.

Important: The HTML-to-DITA converter evaluates two complementary signals when determining the topic type. The converter first evaluates the wording of the heading. It then analyzes the dominant HTML structure beneath that heading. This structure could include paragraphs, ordered lists, tables, or other recurring content patterns. When both signals indicate the same type of content, the converter generates the corresponding DITA topic and body element. It then restructures the HTML content into the child elements required by that topic type.

A Generic topic is the converter's fallback classification when the heading and body content together do not provide sufficient signals to identify a Concept, Task, Reference, or Troubleshooting pattern.
